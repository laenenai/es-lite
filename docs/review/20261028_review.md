- **Review date:** 2026-10-28
- **Module:** `github.com/laenenai/es-lite`
- **Reviewed branch / commit:** `main` @ `dc1691a3c731b365e56a92c18d230e8cc9f44533` (`feat(postgres): OpenWithPool for caller-provided pools`)
- **Working-tree note:** at review time the worktree additionally contained an uncommitted Go `1.27.3` bump in `.mise.toml` and `go.mod` (mtime 2026-10-28 10:11). Code findings are against the committed source; toolchain-dependent results are called out explicitly.
- **Review method:** six parallel expert reviewers (Go/API, event sourcing/backends, security, NATS/JetStream, testing/DX, docs/proto) plus a lead reviewer who inspected the core packages, ran the build/test/lint/security toolchain, and independently reproduced the highest-impact correctness claims in a throwaway copy.

## Executive summary

**Production grade today: NO.**

The code has a coherent core idea, and the happy path builds, tests and runs against real Postgres and NATS. But the public claims, the persisted-data semantics and the failure paths are not yet safe to hand to another engineering team.

The five things that matter most:

1. **The security and GDPR story is not true of this code.** Commit `d451cf4` removed all crypto, `ForgetWorkspace`, the keystore and the `cryptostore` wrapper, but README/ADRs still promise crypto-shredding, ciphertext at rest and PII-safe HMAC uniqueness. The `PII` flag is a no-op and unique-claim values are stored in plaintext. The default NATS “authenticated workspace” cross-check compares a subject token to itself.
2. **Delivery ordering and retry semantics can silently lose or skip events.** `global_position` is a per-database insert sequence, not commit order; Postgres `Drain`/`ReadAll` and JetStream publish order can therefore disagree with it. A consumer that follows the documented global marker can skip events permanently. Poison messages are NAKed immediately and forever, undecodable messages are silently TERMed, and `Nats-Msg-Id = global_position` silently deduplicates different events across databases/cells.
3. **The core event-sourcing API has silent correctness bugs.** An append with zero events skips both the optimistic-concurrency check and the uniqueness constraints. Retries are not idempotent. `LoadAsOfVersion(sid, 0)` returns the whole stream instead of `Initial()`, and as-of-time replay can return a state that never existed because `recorded_at` is sampled before the version check.
4. **Snapshots are a trust boundary, not just a cache.** NATS KV keys are lossy (`a:b_c` and `a_b:c` collide), snapshots carry no store/cell/stream lineage, and `Load` seeds from a snapshot version the log may not contain. A shared or stale bucket can return phantom or cross-tenant state.
5. **Repo and release hygiene is broken.** CI’s integration job calls `test:openbao` and `test:zeroknowledge`, which do not exist; the Docker/Taskfile/CI path still requires a private `natskit` token that is no longer a dependency; there is no lint/format gate (3 files are already unformatted and default `golangci-lint` reports 15 errcheck issues); and the README quickstart does not compile.

## Findings

Each finding has a stable ID, severity, evidence, impact, a concrete recommendation, the compatibility class (API-breaking is cheap; data/wire-format-breaking needs a migration) and an effort estimate. `S` ≈ hours, `M` ≈ 1–3 days, `L` ≈ a week or more.

### Go best practices and idiomatic Go

#### GO-01 — Constructors accept nil/misconfigured dependencies and fail later
- **Severity:** MINOR
- **Evidence:** `aggregate/runtime.go:40-42` accepts nil store/decider/codec; `aggregate/runtime.go:59-64` accepts `WithSnapshots(cache, nil, 0)`; `natsstore/client.go:35-41` accepts a nil `*nats.Conn`; `natsstore/server.go:66-72` accepts a nil Scoper; `delivery/poller.go:66-72` and `delivery/relay.go:41-44` panic instead. `es/store.go` and several interfaces have no documented zero-value behavior.
- **Why it matters:** Misconfiguration becomes a nil-interface panic on the first request, often in a goroutine, rather than a startup error. The mix of “panic”, “nil later” and “return error” is inconsistent for a public library.
- **Recommended change:** Validate required dependencies in constructors; either return `error` (preferred for a library) or panic immediately with a clear message. Make options closed structs/config values where possible. Add tests for each misconfiguration.
- **Breaking:** API-breaking (cheap); no data impact.
- **Effort:** S

#### GO-02 — Read paths silently convert malformed UUIDs, timestamps and versions to zero values
- **Severity:** MINOR
- **Evidence:** `postgres/store.go:250-253` (`e.EventID, _ = uuid.Parse(...)`), `postgres/drain.go:75-78`, `natsstore/conv.go:90-93`, `natsjs/natsjs.go:126-145`, `snapshot/natskv/natskv.go:79`. SQLite validates `EventID` and stream timestamps (`sqlite/store.go:394-405`) but still ignores audit UUIDs at `sqlite/store.go:406-408`.
- **Why it matters:** A corrupt row or hostile NATS message becomes a valid-looking envelope with a nil event ID or zero timestamp. Dedup, audit queries, time travel and consumer idempotency silently degrade; backends also disagree on what they reject.
- **Recommended change:** Centralize envelope/header decoding in one helper that returns wrapped errors for required fields. Treat unparsable persisted data as an error, consistently across SQLite, Postgres, NATS and KV.
- **Breaking:** Behavior tightening only; no data-format change.
- **Effort:** S/M

### Code cleanliness

#### CLN-01 — `cmd/` duplicates observability, NATS connection, health and relay wiring
- **Severity:** MINOR
- **Evidence:** `cmd/es-lited/obs.go:43-136` and `cmd/es-relayd/obs.go:39-133` are near-verbatim copies of `natsConnect`, `initLogging`, `logWriter` and `setupObs`; `cmd/es-lited/main.go:101-121,160-215` and `cmd/es-relayd/main.go:91-134` duplicate health and relay loops, with divergent election behavior. The relay loop is implemented twice.
- **Why it matters:** Fixes land in one binary first; TLS/credential handling already differs (“not replicated here”). Two divergent operational surfaces are a production risk.
- **Recommended change:** Move shared code to `internal/obs`, `internal/natsconn`, `internal/health` and one relay runner; leave `main` as env parsing and wiring.
- **Breaking:** Internal only; no data impact.
- **Effort:** M

#### CLN-02 — Duplicate envelope scanning and overlapping seam types
- **Severity:** NIT
- **Evidence:** `postgres/drain.go:51-85` reimplements the scan in `postgres/store.go:227-256` and has already diverged in error handling. `projection/replay.go:14-21,56-59` re-declares `Source`, `Apply` and a `Marker` interface that no implementation satisfies; `delivery/poller.go:21-35` defines another `Source`/`Checkpoints`. Postgres has a `checkpoints` table but no checkpoint methods.
- **Why it matters:** Validation fixes must be made twice; public seams imply integrations that do not exist.
- **Recommended change:** Reuse `scanEnvelope(rows)` in `Drain`; define one `EventSource` and one checkpoint interface (or alias them); implement or delete `Marker`/Postgres checkpoints.
- **Breaking:** API consolidation is breaking but cheap; no data impact.
- **Effort:** S

### Architecture and internal consistency

#### ARC-01 — `es.Store` encodes SQLite-only ordering guarantees that Postgres cannot honor
- **Severity:** BLOCKER
- **Evidence:** `es/store.go:39-42` defines `ReadAll` as “the delivery cursor the poller tails”; `projection/replay.go:11-15,34` treats workspace-scoped Postgres `ReadAll` as a valid replay source; `postgres/wsstore.go:209-216` implements `global_position > cursor`. But `global_position` is assigned by a sequence at INSERT (`postgres/migrations/0001_initial_schema.sql:10-16`) and rows become visible only at commit: a transaction with `gp=10` can commit after one with `gp=12`. A cursor/replay that has seen 12 never returns 10. `postgres/drain.go:36-41` has the same visibility assumption; with `SKIP LOCKED` and concurrent drains, publish order can differ from `global_position` order (see ES-04, NATS-05).
- **Why it matters:** This is the root architectural defect behind silent event loss for Postgres projections and the “gap-safe” relay claim. The contract tells callers that a guarantee exists that the backend cannot provide.
- **Recommended change:** Decide the ordering contract explicitly (see Q3). For per-stream order, remove/replace `ReadAll` as a global cursor and rebuild consumers on `(stream_id, version)` gap detection. For global order, introduce a single-publisher/watermark or an outbox with `FOR UPDATE SKIP LOCKED` and never advertise N-way publishing.
- **Breaking:** API/contract-breaking; a global-order implementation may add outbox columns (data-format migration). A per-stream redesign does not require a log-format change.
- **Effort:** L

#### ARC-02 — The library-vs-service boundary and crypto ownership boundary are undefined
- **Severity:** MAJOR
- **Evidence:** README advertises both an embedded library and an `es-lited` service (`README.md:6-11`). The service path has no integration test of `natsstore.Server`/`Client` (see TST-03); the pipeline example bypasses it (`examples/pipeline/pipeline_test.go:36-44,78-86`). At the same time, crypto is described as a server/keystore responsibility in README/ADRs but as “the caller's codec” in `postgres/store.go:5-8`, `natsstore/wire.go:6-9` and `snapshot/natskv/natskv.go:1-6`.
- **Why it matters:** External adopters cannot tell which guarantees belong to the module, which to a decorator they must write, and which deployment shape is actually supported. This drives API, test and documentation churn.
- **Recommended change:** Pick a primary consumer (Q2) and write a one-page architecture/ownership contract. If library-first: provide a mandatory `SealingStore`/codec decorator and keep `cmd/` as a reference deployment. If service-first: make the NATS path the tested contract and move library-only concerns behind `internal/`.
- **Breaking:** API/docs depending on choice; no immediate data change.
- **Effort:** M/L

### Security

#### SEC-01 — The default NATS identity check is tautological; es-lited has no authentication
- **Severity:** BLOCKER
- **Evidence:** `natsstore/server.go:83-87` derives the “authoritative” workspace from the subject token; `natsstore/middleware.go:84-93` then compares that same subject token to it. `HeaderIdentity` (`middleware.go:49-53`) trusts an arbitrary client header. `README.md:80-86` claims a fail-closed cross-check against the authenticated workspace. No JWT/auth-callout extractor exists in the repo; `docs/deploy/README.md:165-171` lists per-workspace NATS ACLs as a prerequisite.
- **Why it matters:** Any principal allowed to publish `svc.eslite.<ws>.<method>` can read/write that workspace. The code looks like an authorization gate but verifies nothing; trusting it without broker ACLs is a tenant-isolation breach.
- **Recommended change:** Make an authenticated `IdentityExtractor` mandatory (from a verified NATS user JWT or auth-callout stamp) and fail startup without it. Treat `HeaderIdentity` as trusted-proxy-only and document that. Add an integration test publishing to another workspace's subject. Keep subject ACLs as defense in depth.
- **Breaking:** API/config-breaking (cheap); no data-format change.
- **Effort:** M

#### SEC-02 — TLS is documented but not enforced; sample manifests use plaintext NATS
- **Severity:** MAJOR
- **Evidence:** `cmd/es-lited/obs.go:39-42` explicitly says natskit’s TLS env handling was not replicated; `natsConnect` (`obs.go:46-66`) sets no `nats.Secure`, root CA or client certificate. `deploy/k8s/deployment.yaml:60` and `relay.yaml:38` use `nats://`. No Postgres DSN validation enforces `sslmode=verify-full`. README claims mTLS on the client/service hop (`README.md:98-99`).
- **Why it matters:** Payloads may be ciphertext by policy, but metadata (workspace, actor, stream IDs, type URLs, claim scopes), NATS credentials and Postgres traffic can cross the network in clear. The documented security model is not the deployed one.
- **Recommended change:** Add `NATS_CA`/`NATS_CERT`/`NATS_KEY` and wire `nats.RootCAs`/`ClientCert`/`Secure`; require `tls://` in production. Validate Postgres DSNs or document a hard `sslmode=verify-full` requirement and enforce it at startup.
- **Breaking:** Ops/config-breaking; no data impact.
- **Effort:** S/M

#### SEC-03 — Six reachable dependency vulnerabilities and no vulnerability gate
- **Severity:** MAJOR
- **Evidence:** The `govulncheck` run above reports reachable issues in `golang.org/x/text v0.40.0`, `golang.org/x/net v0.57.0` and `google.golang.org/grpc v1.83.0`; `go.mod:40,43,46`. CI has no `govulncheck` task/action (`Taskfile.yml:57-107`, `.github/workflows/ci.yml:13-23`).
- **Why it matters:** Some traces are over-approximated, but the modules have fixes available and the project has no way to notice the next regression. A production library should gate on reachable vulnerabilities.
- **Recommended change:** Bump to `x/text@v0.41.0`, `x/net@v0.60.0`, `grpc@v1.83.1`; add a pinned `govulncheck` Taskfile target and CI job; add dependency update automation.
- **Breaking:** No; dependency update only.
- **Effort:** S

#### SEC-04 — Lossy sanitization makes KV keys and NATS subjects collide across streams/workspaces
- **Severity:** MAJOR
- **Evidence:** `snapshot/natskv/natskv.go:62-64,98-108` maps every non-`[A-Za-z0-9_-]` rune to `_`; valid stream IDs `counter:a_b` and `counter_a:b` both become `ws.counter_a_b`. Workspace `a.b` and `a_b` collide too. `natsjs/natsjs.go:57-64,76-88` applies the same substitution to workspace/aggregate/event tokens and lowercases event types, so distinct subjects can collapse.
- **Why it matters:** A snapshot can seed another stream's/tenant's state; a projection filtering `evt.<ws>.>` can receive another workspace's events. With plaintext snapshots this is a data leak, not just a cache bug.
- **Recommended change:** Use an injective encoding (`base64.RawURLEncoding` or length-prefixed components) and validate workspace IDs as slugs. Add explicit collision tests for both KV and NATS subjects.
- **Breaking:** Data/cache-format change (old snapshot keys orphan safely); NATS subject change is wire-breaking for consumers.
- **Effort:** S/M

#### SEC-05 — Errors leak internal details and PII; credentials can be logged
- **Severity:** MINOR
- **Evidence:** `natsstore/wire.go:138-154` maps unknown errors to `err.Error()`; `postgres/wsstore.go:164-167` and `sqlite/store.go:271-286` interpolate `op.Value` into returned error messages. `cmd/es-lited/obs.go:50-52` and `cmd/es-relayd/obs.go:46-48` log `nc.ConnectedUrl()`, which can include userinfo; `nats.ConnectedUrlRedacted()` exists. `natsstore/middleware.go:127-132` discards `req.Respond` errors.
- **Why it matters:** Database/schema details and raw claim values can cross the NATS hop and land in client or central logs; NATS credentials can land in stdout/OpenObserve.
- **Recommended change:** Return stable error codes with a correlation ID; log details server-side only. Never interpolate claim values. Use `ConnectedUrlRedacted`. Check `Respond`/`Error` send errors.
- **Breaking:** No; behavior tightening.
- **Effort:** S

#### DX-04 — Go toolchain mismatch and generated-code drift
- **Severity:** MAJOR

- **Breaking:** No; generated comment formatting only.
- **Effort:** S

### Event-sourcing correctness

#### ES-01 — Empty append silently skips optimistic concurrency and constraints
- **Severity:** BLOCKER
- **Evidence:** `sqlite/store.go:164-166` and `postgres/wsstore.go:39-41` return success for `len(p.Events)==0` without checking `ExpectedVersion` or applying `Constraints`; `aggregate/runtime.go:98-101` returns before calling `Append` at all. Reproduced: `Append{ExpectedVersion:999, Constraints:[Claim("email","a@b.com",true)]}` returns `err=nil`, `LookupClaim` is false; a stale empty append after v1 also returns nil instead of `ErrConflict`.
- **Why it matters:** A claim/release-only command is silently lost, and a stale writer can believe it committed. Uniqueness can be bypassed by a command that happens to produce no events.
- **Recommended change:** Always run the version check and claim transaction; in `Runtime.Handle`, call `Append` when `len(events)>0 || len(constraints)>0`. Reject unknown `ConstraintOpKind` values instead of skipping them. Add regression tests for both backends.
- **Breaking:** Behavior tightening (cheap API); no data-format change.
- **Effort:** S

#### ES-02 — Appends are not idempotent; ambiguous retries duplicate business events
- **Severity:** BLOCKER
- **Evidence:** `aggregate/runtime.go:103-114` lets the store mint a new event ID on every attempt (`sqlite/store.go:200-203`, `postgres/wsstore.go:73-76`). A retry after a committed-but-ambiguous append (NATS client timeout is 5s, `natsstore/client.go:60-67`) reloads the new version and re-executes `Decide`, appending a second event. `CommandID` is audit metadata only; runtime mints a new one if zero (`aggregate/runtime.go:119-121`). Duplicate `event_id` is mapped to `ErrConflict` (`postgres/wsstore.go:93-96`; SQLite maps any constraint error at `sqlite/store.go:216-220`), so callers retry again.
- **Why it matters:** At-least-once transport plus no dedup equals duplicated domain events. For an event-sourcing library this is a data-integrity blocker, not an optimization.
- **Recommended change:** Require a caller-supplied stable `CommandID` and add a dedup table keyed by `(workspace, command_id)` storing the committed version range/result; or derive event IDs deterministically from `(CommandID, index)` and return the stored envelopes on duplicate. Add an `ErrDuplicate` distinct from `ErrConflict` and narrow constraint mapping. Existing duplicate command IDs need cleanup before adding a unique index.
- **Breaking:** Additive API; data-format migration (new table/index + cleanup).
- **Effort:** L

#### ES-03 — `recorded_at` is not monotonic per stream, so as-of-time replay can skip versions
- **Severity:** BLOCKER
- **Evidence:** Postgres uses `timestamptz DEFAULT now()` (`postgres/migrations/0001_initial_schema.sql:24`), which is transaction start; SQLite samples `time.Now()` before `BeginTx` (`sqlite/store.go:168-174`). If transaction B starts earlier but commits after A, B's later version gets an earlier `recorded_at`. `ReadStreamAsOf` filters `recorded_at <= ?` and orders by version (`postgres/wsstore.go:196-203`, `sqlite/store.go:308-315`), so it can return v2 without v1; `aggregate.load` folds v2 onto `Initial()` and returns a state that never existed.
- **Why it matters:** Time travel is a headline feature; a wrong as-of state is silent and unrecoverable from the user's perspective.
- **Recommended change:** Sample the timestamp at INSERT after the version check (`clock_timestamp()` in Postgres, `time.Now()` after the version read in SQLite), or derive as-of ordering from a monotonic per-stream sequence. Add a two-transaction regression test. Existing rows may violate monotonicity; document or backfill.
- **Breaking:** No API change; as-of data semantics/possible backfill.
- **Effort:** M

#### ES-04 — Global ordering is claimed but not preserved by the relay/JetStream path
- **Severity:** BLOCKER
- **Evidence:** `postgres/drain.go:36-41` claims rows with `published_at IS NULL ORDER BY global_position FOR UPDATE SKIP LOCKED` and publishes before commit. A lower `gp` row can be invisible while a higher one is visible; with overlapping drains (the sanctioned two-leader overlap, or N-way `es-relayd`), disjoint batches can publish out of order. JetStream orders by publish sequence. ADR 0005 tells consumers to skip events whose `gp` is at or below their marker (`docs/adr/0005:48-50`), so a reordered higher `gp` causes the lower event to be skipped permanently in the live read model.
- **Why it matters:** This is silent event loss for projections, even though the DB retains the event. The documented consumer contract makes it worse.
- **Recommended change:** Choose and enforce one contract (Q3): per-stream ordering with version gap detection, or global ordering via a single publisher/visibility watermark/outbox. Do not advertise N-way publish safety until it is true. Add a concurrent-drain/reordering test.
- **Breaking:** API/documentation contract; a global-order outbox adds schema (migration).
- **Effort:** L

#### ES-05 — `LoadAsOfVersion(0)` returns the current state; future versions do not error
- **Severity:** MAJOR
- **Evidence:** `aggregate/runtime.go:177-181` documents “v=0 returns Initial()” but passes 0 to `load`; `load` treats `upToVersion==0` as unbounded (`runtime.go:213-240`), matching `es/store.go:26-31`. Reproduced: after Init(5)+Increment(10), `LoadAsOfVersion(0)` returns count 15; `LoadAsOfVersion(99)` also returns 15 with no error.

- **Recommended change:** Special-case `v==0` to return `decider.Initial()`/version 0; introduce an explicit bounded flag in `load`; return an error for `v > current`. Add table tests for 0, 1, current, current+1.

#### ES-06 — Snapshots are trusted without log/store lineage
- **Severity:** MAJOR
- **Evidence:** `aggregate/runtime.go:222-230,246` seeds `state` and `from=snap.Version` from any snapshot with a matching `FoldVersion`, without checking that the log contains that version. `snapshot.Snapshot` (`snapshot/snapshot.go:20-25`) carries no stream ID, database/cell identity or codec identity. `examples/snapshots/snapshots_test.go:94-104` explicitly asserts that an empty store returns count 15/version 3 from the snapshot alone. `LoadStale` returns cache-only state with `fresh=true` (`runtime.go:199-205`), so the name is misleading.

#### BE-02 — Migration locking is unsafe in both backends

### Crypto-shredding and erasure

#### CRY-01 — Crypto-shredding and GDPR erasure are absent, but still claimed
- **Severity:** BLOCKER
- **Evidence:** `d451cf4` removed `keystore/`, `shred/`, `cryptostore/`, wrapped-DEK RPCs and `ForgetWorkspace`. `postgres/store.go:5-8` and `sqlite/store.go:204-214` insert `ev.Payload` verbatim. No `ForgetWorkspace`, key deletion, projection purge or JetStream/KV purge exists.
- **Why it matters:** Unless every client independently encrypts and shreds, the database, backups, WAL, JetStream and KV retain plaintext. The library's central erasure claim is false.
- **Recommended change:** Decide the product position (Q1). If keeping zero-knowledge: remove all server-side shredding/GDPR claims, make client sealing/erasure an explicit, documented responsibility, and optionally ship a client-side sealing/shred package. - **Effort:** L

#### CRY-02 — `PII` is a dead flag; no client sealing helper exists
- **Severity:** BLOCKER
- **Evidence:** `es/constraint.go:23-27` says backends with a keystore persist a keyed hash for `PII: true`; `es/store.go:48-52` says a PII claim is looked up by the same keyed HMAC. Both backends ignore the flag: `postgres/wsstore.go:173-179` returns `[]byte(op.Value)`, and SQLite says “PII is a Postgres concern” (`sqlite/store.go:261-262`) while also storing plaintext. `LookupClaim(..., pii)` ignores `pii`. No sealing codec/decorator is provided.
- **Why it matters:** Callers who set `PII: true` store email addresses and identifiers in plaintext, including in the primary-key index and backups. Existing deleted `cryptostore` stored base64 HMACs, so old and new claims would not collide anyway.
- **Recommended change:** Either remove `PII`/`pii` from the API and document that callers must pre-hash/seal (with a provided decorator), or implement a mandatory client-side HMAC decorator and reject plaintext PII at the store boundary. Do not silently accept the flag. Migrate/dual-read existing claims if changing the key format.

#### CRY-03 — Snapshots and unique claims are plaintext; erasure does not cover them

- **Why it matters:** Folded aggregate state and uniqueness keys often contain PII; even if events are client-sealed, these surfaces remain readable after a workspace is “forgotten”.
- **Recommended change:** Require an authenticated/sealing codec for snapshots; bind them to workspace/stream/version; purge snapshots and claims as part of any erasure operation. If erasure is not provided, document that these surfaces are caller-owned and must be encrypted/purged by the client.
- **Breaking:** Cache/value format change (rebuildable); claims migration if hashing introduced.
- **Effort:** M

#### CRY-04 — JetStream, backups, indexes and WAL are outside the erasure story
- **Severity:** MAJOR
- **Evidence:** `natsjs/publisher.go:79-85` publishes payloads to JetStream; `EnsureStream` has no purge path (`publisher.go:45-61`). Postgres `unique_claims` has a primary-key index over `value_key`; SQLite stores plaintext values. No code deletes rows from `events`, `unique_claims`, checkpoints, JetStream streams or KV buckets after a workspace deletion.
- **Why it matters:** Crypto-shredding only works if ciphertext is the only copy and the key is destroyed everywhere. The current system has multiple plaintext/derived copies and no destructive workflow.
- **Recommended change:** Define an erasure workflow that covers the source log, indexes, snapshots, JetStream (including replicas/backups), KV and any read models; test it end to end. If not implementing, remove the erasure guarantee and publish a data-retention matrix.
- **Breaking:** Ops/data lifecycle; no API change.
- **Effort:** L

### NATS / JetStream delivery

#### NATS-01 — Poison messages hot-loop forever; one event blocks the projection
- **Severity:** BLOCKER
- **Evidence:** `natsjs/consumer.go:33-37` creates a consumer with only `Durable`, `AckPolicy` and `FilterSubject`; NATS defaults are `MaxDeliver=-1` and `AckWait=30s`. On handler error, `consumer.go:48-52` calls `msg.Nak()` with no delay. `Consume` runs one serial callback, so a permanently failing event blocks every later event matching the filter.
- **Why it matters:** A bad schema, decrypt failure or read-model bug creates an infinite redelivery loop that consumes CPU and stops the projection. This is the most common production failure mode for a durable consumer.
- **Recommended change:** Add explicit `MaxDeliver`, `AckWait`, `BackOff`, `MaxAckPending` and a retryable/permanent error classification; use `NakWithDelay` with exponential backoff, then publish to a DLQ and `Term`. Add a test with a permanently failing message.
- **Breaking:** Additive config; behavior change; no wire break.
- **Effort:** M

#### NATS-02 — Undecodable messages are silently TERMed with no DLQ, log or metric
- **Severity:** BLOCKER
- **Evidence:** `natsjs/consumer.go:42-47` calls `msg.Term()` on `DecodeEnvelope` error and returns. There is no log, metric, dead-letter subject or alert; `Ack`/`Nak` errors are also discarded (`:49-52`).
- **Why it matters:** A version-skew rollout (producer emits a new type before the consumer knows it) or malformed header permanently skips the event for that durable. The event remains in the DB but is absent from the live read model until a manual rebuild.
- **Recommended change:** Distinguish poison/version-skew from transient errors; route undecodable events to a DLQ with the original headers/body and a reason; log/metric the event ID. Never silently Term every decode error.
- **Breaking:** Consumer behavior; no data format change (new DLQ subject).
- **Effort:** S/M

#### NATS-03 — `Nats-Msg-Id = global_position` is not globally unique
- **Severity:** BLOCKER
- **Evidence:** `natsjs/natsjs.go:97` sets the dedup ID to `global_position`; the comment/ADR calls it globally unique. It is unique per database sequence (`postgres/migrations/0001...:10-16`, `sqlite/migrations/0001...:13-14`). Every SQLite database starts at 1, and a restored/cloned Postgres database or another cell sharing the same stream reuses positions. JetStream dedups stream-wide within its window, first wins.
- **Why it matters:** Distinct events are silently dropped from live consumers when two sources share a stream. The DB still has them, so the failure is invisible until a rebuild.
- **Recommended change:** Use a source-incarnation-scoped key: `<db-incarnation>/<gp>`, `<workspace>/<event-id>` (UUIDv7 is backup-stable), or persist a stable database UUID. Keep `global_position` as an ordering header. Size the dedup window for the maximum retry path.
- **Breaking:** Wire/dedup-key change; structurally compatible headers, one-time duplicate window at rollout.
- **Effort:** S

#### NATS-04 — Leader lease outlives the work it elects
- **Severity:** BLOCKER
- **Evidence:** `leader/leader.go:67-75`: `onLeader` runs in a goroutine; `hold` refreshes the lease until the outer context ends and does not watch the `done` channel. `cmd/es-lited/main.go:205-210` returns from `onLeader` when `relay.Run` errors; the lease keeps being refreshed with no relay running, so every other replica stays a follower.
- **Why it matters:** The cluster has a healthy-looking leader that does no delivery until that process restarts. This is exactly the failure path after a transient NATS/Postgres error.
- **Recommended change:** `hold` must select on `done` and delete/stop refreshing the key when `onLeader` returns early; surface the error and either retry or terminate. Only step down on definitive revision/not-found errors; retry transient `Update` failures. Delete the key on graceful shutdown. Add a test where the callback exits early.
- **Breaking:** No API change required; returning an error from `onLeader` would be cleaner but is API-breaking.
- **Effort:** S

#### NATS-05 — `Drain` + `SKIP LOCKED` can publish a stream's events out of order
- **Severity:** MAJOR
- **Evidence:** `postgres/drain.go:36-41,95-108` claims a batch, publishes it sequentially, then marks `published_at` in the same transaction. Two drainers (sanctioned overlap or N-way `es-relayd`) can hold disjoint batches; if a stream has v1 at gp 50 and v2 at gp 150, v2 can publish first. JetStream preserves publish order, not DB order. `natsjs` says N-way publishing is safe (`natsjs.go:8-10`), and `relay.yaml:9-12` calls concurrent drains “harmless”.
- **Why it matters:** Per-stream ordering is broken even if the global marker contract is fixed; consumers that rely on version order can apply v2 before v1.
- **Recommended change:** Single-flight the claim+publish+mark sequence (advisory lock/lease fencing), or shard by stream and guarantee one drainer per stream, or change the consumer contract to version-based buffering. Do not advertise N-way safety without the mechanism.
- **Breaking:** Deployment/throughput trade-off; no data format change.
- **Effort:** M

#### NATS-06 — Consumer configuration is implicit and `Consume` never notices a dead consumer
- **Severity:** MAJOR
- **Evidence:** `natsjs/consumer.go:33-37` pins every field except durable/ack/filter; `Consume` waits only on `ctx.Done()` (`:57-60`) and never selects on `cc.Closed()`. There are no `DeliverPolicy`, `AckWait`, `MaxDeliver`, `BackOff` or pull-batch options. The KEDA example autoscales one durable to 10 replicas (`deploy/k8s/keda-scaledobject.yaml:41-49`, `docs/deploy/README.md:139-140`), which distributes batches of the same consumer across goroutines and breaks per-stream order.
- **Why it matters:** Ops cannot tune retry/flow control; a deleted consumer or revoked permission silently stops projection while the process stays healthy; autoscaling a single ordered durable is unsafe.
- **Recommended change:** Expose a full `jetstream.ConsumerConfig` (with explicit defaults), use `CreateConsumer`/`UpdateConsumer` deliberately, select on `cc.Closed()`, add per-message timeout, and run one active consumer per durable or shard by stream. Document the ordering/throughput trade-off.
- **Breaking:** Additive config; deployment behavior change; no wire break.
- **Effort:** M

#### NATS-07 — Relay treats the first error as fatal; health does not reflect relay liveness
- **Severity:** MAJOR
- **Evidence:** `delivery/relay.go:60-62` returns on the first drain error; `cmd/es-relayd/main.go:108-109` calls `log.Fatalf`; `cmd/es-lited/main.go:207-209` logs and returns from the leader callback. `/healthz` checks only `nc.IsConnected()` (`cmd/es-lited/main.go:102-109`, `cmd/es-relayd/main.go:120-127`). There is no retry/backoff, last-success timestamp, lag metric or readiness signal.
- **Why it matters:** A transient NATS/Postgres blip kills delivery (or leaves a dead leader), while Kubernetes reports healthy. Poison rows crash-loop the relay.
- **Recommended change:** Retry transient errors with bounded backoff; classify permanent errors and quarantine; exit the process on unrecoverable failure; export last-publish/lag and fail readiness when stalled.
- **Breaking:** Behavior change; no wire/data change.
- **Effort:** S/M

#### NATS-08 — `EnsureStream` auto-creates unbounded R1 streams and rewrites ops-provisioned topology
- **Severity:** MAJOR
- **Evidence:** `natsjs/publisher.go:53-60` calls `CreateOrUpdateStream` with `MaxAge` as given; `MaxAge: 0` means unlimited, not “per server limits” (`publisher.go:40-42` comment). `ES_ENSURE_STREAM` defaults to true (`cmd/es-lited/main.go:174-179`, `cmd/es-relayd/main.go:85-89`), so a dev default becomes R1/infinite retention. `CreateOrUpdateStream` updates existing streams, so a replica can rewrite an ops-provisioned R3/bounded stream; if the update fails, the relay exits. Bounded retention also creates silent consumer gaps because `Consume` never compares the ack floor to `FirstSeq`.
- **Why it matters:** Unbounded streams exhaust disk; updating production topology from every replica is dangerous; retention gaps cause permanent projection misses.
- **Recommended change:** Make stream creation create-only in production, require explicit `MaxAge`/`MaxBytes` defaults, run `EnsureStream` only after leadership, and check `AckFloor < FirstSeq` at startup (fail readiness/force DB rebuild).
- **Breaking:** Deployment/config change; no wire break.
- **Effort:** S/M

### Proto and schema evolution

#### PROTO-01 — `buf breaking` is configured but never run; `generate:check` misses untracked files
- **Severity:** MAJOR
- **Evidence:** `buf.yaml:8-10` sets `breaking.use: [FILE]`, but `Taskfile.yml:104-107` only runs `buf lint` despite its description claiming a breaking check; CI runs only `generate:check` (`ci.yml:21`). `generate:check` uses `git diff --exit-code -- gen/` (`Taskfile.yml:46-50`), which ignores untracked generated files.
- **Why it matters:** Removed fields/variants or changed types can merge silently; a new proto can generate a new untracked file that CI accepts. The gate claims protection it does not provide.
- **Recommended change:** Add `buf breaking --against` a stable baseline/tag or the PR base SHA to `lint:proto` and CI; make `generate:check` use `git status --porcelain -- gen/` (or `git add -N gen/` then diff).
- **Breaking:** No; generated files only.
- **Effort:** S

#### PROTO-02 — The NATS service wire is unversioned JSON, not the proto contract ADR 0009 claims
- **Severity:** MAJOR
- **Evidence:** `natsstore/wire.go:34-134` defines hand-written JSON structs; there is no protocol version field and no proto request/reply messages. ADR 0009 says “Requests and replies are proto messages” (`docs/adr/0009:188`). JSON silently ignores unknown fields and zero-fills missing ones.
- **Why it matters:** Client and server cannot evolve independently; renaming/removing a JSON field is a silent wire break that `buf breaking` cannot see. A mixed rollout can produce zero-valued `EventID`, timestamps or versions.
- **Recommended change:** Define generated, versioned proto request/reply messages (e.g. `eslite.store.v1`) with reserved ranges, or explicitly document JSON-v1 as additive-only and add a protocol version plus compatibility tests. Include the chosen contract in the breaking gate.
- **Breaking:** Wire-format change; requires a migration/dual-protocol window for deployed clients.
- **Effort:** L

### Operations and observability

#### OPS-01 — Health checks only NATS connectivity
- **Severity:** MAJOR
- **Evidence:** `cmd/es-lited/main.go:102-109` and `cmd/es-relayd/main.go:120-127` return 200 whenever `nc.IsConnected()`. They do not check Postgres/pool health, migration state, JetStream/stream existence, relay leadership or consumer lag. Readiness and liveness use the same endpoint (`deploy/k8s/deployment.yaml:86-93`, `relay.yaml:47-54`).
- **Why it matters:** A pod with a dead database or stalled relay is reported healthy and keeps receiving traffic; Kubernetes cannot distinguish “alive” from “useful”.
- **Recommended change:** Separate liveness (process/NATS) from readiness (DB ping, schema version, relay/consumer progress). Return degraded status when the store or relay is unavailable; expose last-success/lag gauges.
- **Breaking:** Ops behavior; no data change.
- **Effort:** S/M

#### OPS-02 — No relay/consumer lag or last-success metrics; auto-created stream retention is unbounded
- **Severity:** MAJOR
- **Evidence:** `cmd/es-lited/main.go:186-193` and `cmd/es-relayd/main.go:94-101` export only a `eslite.relayed` count. There is no last-publish timestamp, drain lag, dead-letter count, consumer pending/ack-floor metric or alert. `ES_ENSURE_STREAM` defaults on and `EnsureStream` has no default `MaxAge` (NATS-08).
- **Why it matters:** Operators can see throughput but not whether the relay is keeping up, stalled or silently dropping events; an unbounded stream is an outage waiting to happen.
- **Recommended change:** Export `relay_last_success_timestamp`, `relay_lag_events`, `consumer_pending`, `consumer_ack_floor` and DLQ counts; alert on staleness. Require an explicit retention bound in production.
- **Breaking:** Additive observability; no data change.
- **Effort:** S/M

## Cross-cutting themes

1. **Post-refactor documentation and API drift dominates.** `d451cf4` removed crypto and `e1114ce` removed natskit, but README, ADRs, deploy docs, Dockerfile, Taskfile, CI and release still describe the removed stack. The most security-sensitive claims are now false, not merely stale.
2. **SQLite’s guarantees leaked into the public contract.** `ReadAll` as a gap-free cursor, `GlobalPosition` as universal delivery identity and `RecordedAt` as commit time are true only for single-writer SQLite. Postgres cannot implement them without an outbox/visibility layer. Findings ARC-01, ES-03, ES-04, BE-01, NATS-03 and NATS-05 share this root cause.
3. **Identity is overloaded.** `global_position` is used as delivery cursor, NATS dedup ID and row identity; `event_id` is a uniqueness key but not an idempotency key; `command_id` is audit metadata but not enforced. Define separate identities: per-stream version, per-database global position, globally unique event ID and command idempotency key.
4. **Snapshots and leases are treated as caches/leases without lineage or liveness.** Snapshot keys are lossy, snapshots carry no store/stream identity, and leader leases are refreshed independently of whether the elected work is running. Both can outlive their source of truth.
5. **The suite is green by skipping.** The core runtime, transport, migration and CLI packages have no package-level tests; the integration suites are opt-in, destructive and split across tasks. Every blocker above is a failure mode the current suite cannot catch.
6. **Failure classification is inverted.** Permanent data errors are retried forever (consumer NAK) or become process-fatal (relay publish), while a dead consumer or stalled relay is silent and healthy. Production correctness depends on an unspecified handler/operator contract.
7. **Gates are nominal.** No lint/format/race/coverage/vulnerability gate, `buf breaking` is dead config, `generate:check` misses untracked files, and CI calls tasks that do not exist. The build is reproducible only by accident.

## Open questions for the maintainer

These are decisions only the maintainer can make. Each is standalone and includes a recommendation. They will shape the implementation plan; answer one at a time.

### Q1 — Is crypto-shredding a product requirement of this module, or is the module deliberately zero-knowledge with client-owned crypto?

**Context:** `d451cf4` removed `keystore`, `shred`, `cryptostore`, `ForgetWorkspace` and all server-side crypto. README/ADRs 0004/0006/0008 still promise per-workspace OpenBao KEKs, `ForgetWorkspace`, ciphertext at rest and HMAC’d PII claims. The `PII` flag is now ignored and claim values are plaintext.

**Why it blocks:** It determines whether we restore a large subsystem and migrate existing plaintext data, or rewrite the public security contract and add a client-side sealing helper. It changes the API surface, the data format, the test matrix and the docs.

**Options:**
- **A (recommended):** Keep the server zero-knowledge. Remove server-side shredding/GDPR claims, remove or redefine `PII`, and ship an optional client-side sealing/erasure package (`cryptostore`/`shred`) with examples. No server data migration; existing plaintext stays plaintext unless clients rewrite.
- **B:** Restore server-side per-workspace envelope encryption + keystore + `ForgetWorkspace`. This reverses ADR 0025, adds key custody/backups, and requires a migration/backfill of existing plaintext events/claims/snapshots.
- **C:** Be an opaque event store with no crypto story at all. Remove all encryption/erasure language and the `PII` flag; callers own everything. Simplest, but gives up the “zero-knowledge” selling point.

**Recommendation:** A. It preserves the current architecture and the strongest honest claim (“the server never sees keys”) while still giving adopters a supported client-side path.

### Q2 — Is the primary consumer an embedded Go library, an operated NATS service, or both?

**Context:** README advertises both. Tests mostly cover the embedded library; `natsstore.Server`/`Client` have no end-to-end test, and `examples/pipeline` bypasses the service.

**Why it blocks:** It sets which API is public/stable, which path gets the integration suite, how much operational hardening (auth/TLS/health/streams) is in scope, and whether `cmd/` is a supported product or a reference deployment.

**Options:**
- **A (recommended):** Library-first; `es-lited` is a reference deployment, clearly marked as such until the NATS security/delivery work lands.
- **B:** Service-first; make the NATS wire/auth/ops contract primary and demote embedded use.
- **C:** Both equally; fund two conformance/integration suites and keep both contracts stable.

**Recommendation:** A now, revisit after Q7/Q9. It matches the current code quality distribution and avoids promising a production service before it is tested.

### Q3 — What ordering guarantee should the public contract make?

**Context:** `global_position` is claimed to be total order, but Postgres assigns it before commit and the relay/JetStream publish order can differ. `ReadAll` is used as a global cursor and `projection.Marker` tells consumers to skip positions at/below their marker. A lower position can become visible after a higher one.

**Why it blocks:** It determines the redesign of `ReadAll`, `Drain`, the consumer marker, and the NATS headers. “Global order” requires a single publisher/watermark/outbox; “per-stream order” is cheaper and matches event-sourcing usage but changes the public contract.

**Options:**
- **A (recommended):** Guarantee per-stream order only (`StreamID`, `Version`); treat `GlobalPosition` as an opaque delivery cursor, remove it from the consumer correctness contract, and rebuild projections with per-stream version gap detection.
- **B:** Guarantee global order with a single publisher/visibility watermark or an outbox; accept lower relay throughput and schema work.
- **C:** Best-effort order with an explicit caveat. Not acceptable for a production event store.

**Recommendation:** A. Most aggregates need per-stream order; global order is expensive and the current code cannot deliver it.

### Q4 — What is the idempotency contract for appends?

**Context:** Retries after an ambiguous commit re-execute `Decide` and append duplicates because the runtime mints fresh event IDs and does not dedup `CommandID`. A caller-supplied duplicate `EventID` is misreported as `ErrConflict`.

**Why it blocks:** It adds a dedup table/index and a new result/error contract, and it interacts with the ordering and NATS dedup design. Existing data may contain duplicate command IDs.

**Options:**
- **A (recommended):** Require a caller-supplied stable `CommandID`; add a dedup table keyed by `(workspace, command_id)` storing the committed result; return the original result on retry. Add `ErrDuplicate` distinct from `ErrConflict`; clean existing duplicates before the unique index.
- **B:** Derive event IDs deterministically from `(CommandID, index)` and return stored envelopes on duplicate. Smaller API, but callers still need stable CommandIDs and event IDs become less opaque.
- **C:** No server-side dedup; require callers to use at-most-once semantics. Not acceptable for a production event store.

**Recommendation:** A. It gives the strongest guarantee with a clear migration path.

### Q5 — Are SQLite and Postgres both production-supported, or is SQLite dev/edge only?

**Context:** SQLite lacks `workspace_id`/RLS and a conformance suite; `cmd/es-lited` ignores the workspace argument for SQLite, so every NATS workspace token shares one store. Postgres is described as the production backend, SQLite as dev/edge.

**Why it blocks:** It determines whether we add `workspace_id` to SQLite and enforce it, or restrict/remove the SQLite service path; it also scopes the backend conformance suite and the migration work.

**Options:**
- **A (recommended):** SQLite is dev/edge only; reject non-empty workspace tokens in the SQLite scoper (or bind to one configured workspace), and document that the NATS multi-workspace service requires Postgres.
- **B:** Full parity: add `workspace_id`/RLS-equivalent filtering to SQLite, enforce it, and run one conformance suite against both backends.
- **C:** Drop SQLite.

**Recommendation:** A. It matches the current design and avoids pretending SQLite is a multi-tenant backend.

### Q6 — Is there existing production data that must be migrated?

**Context:** The event log, snapshots and unique claims are persisted. Fixes for idempotency, as-of timestamps, ordering/outbox, PII hashing and crypto may add columns/tables or change semantics. The README says pre-1.0.

**Why it blocks:** It decides whether we can reset schema/format (cheap) or must write forward migrations/backfills with dual-read windows (expensive, and some fixes become much harder).

**Options:**
- **A (recommended):** No production data yet; treat v0.x as resettable, but still write forward migrations for any schema change.
- **B:** Small amount of data; write forward-only migrations and a backfill plan, no hard resets.
- **C:** Real production data; freeze schema changes, require migration/rehearsal/rollback plans and compatibility windows.

**Recommendation:** A, if confirmed. If any data exists, switch to C before implementing ES-02/ES-03/CRY-02.

### Q7 — What is the authentication/authorization model: NATS ACLs only, or authenticated identity from an auth callout/JWT?

**Context:** The default `IdentityExtractor` derives the workspace from the subject and the middleware compares it to the same subject. `HeaderIdentity` trusts a client header. No JWT/auth-callout extractor exists in the repo.

**Why it blocks:** It determines whether `NewServer` can fail startup without an extractor, what the deployment prerequisite is, and how the cross-workspace test is written. It also affects whether `HeaderIdentity` remains public.

**Options:**
- **A (recommended):** Require an authenticated extractor (NATS user JWT or auth-callout-stamped identity); fail startup without one; keep subject ACLs as defense in depth.
- **B:** Trust per-workspace NATS subject ACLs only; document them as a hard prerequisite and remove the misleading app-level “cross-check” claim.
- **C:** Add a signed request envelope/claims; more work, but works across non-NATS transports.

**Recommendation:** A. It makes the code’s security claim true and gives external adopters a clear integration point.

### Q8 — Should the NATS service wire stay JSON or move to versioned proto?

**Context:** ADR 0009 says proto; the code uses unversioned JSON structs. There is no protocol version, and JSON silently accepts missing/unknown fields.

**Why it blocks:** It is a wire-format decision. Moving to proto is a wire-breaking change and adds codegen; keeping JSON requires an explicit additive-only policy and a version field.

**Options:**
- **A (recommended):** Define versioned proto request/reply messages (`eslite.store.v1`) with reserved ranges; generate them with buf; include them in the breaking gate.
- **B:** Keep JSON but add a protocol version and an additive-only compatibility test; document it as v1.
- **C:** Freeze the wire as Go-to-Go only; no external SDK promise.

**Recommendation:** A while pre-1.0. It matches the ADR and supports the stated multi-language ambition.

### Q9 — What should `natsjs.Consume` guarantee: ordered single-active, concurrent at-least-once, or exactly-once?

**Context:** The adapter creates one durable with defaults (unlimited deliveries, immediate NAK, no DLQ, no consumer-death detection); the KEDA example autoscales one durable to 10 replicas. “Exactly-once” is not possible without a dedup store; at-least-once is claimed but the consumer policy is missing.

**Why it blocks:** It determines the consumer API, retry/DLQ design, autoscaling guidance and whether `MaxAckPending=1`/single-active is enforced.

**Options:**
- **A (recommended):** Ordered single-active consumer per durable, bounded retry with backoff + DLQ; autoscale by sharding into separate durables, not by replicas of one durable.
- **B:** Concurrent at-least-once with explicit idempotency/commutativity requirements; higher throughput, weaker ordering.
- **C:** Exactly-once via a dedup store. Complex; only if a real use case requires it.

**Recommendation:** A. It matches event-sourcing read models and the current single-callback implementation.

### Q10 — Keep NATS KV snapshots, or remove them until correctness/security is fixed?

**Context:** Snapshots are an optional optimization. They have lossy keys, no store/stream lineage, plaintext storage, no CAS, and can seed phantom state. Removing them simplifies the security and correctness story; keeping them requires sealed, lineage-bound values and a migration of cache keys.

**Why it blocks:** It scopes CRY-03/ES-06/SEC-04/TST-04. If removed, we delete a package and a pile of failure modes; if kept, we design an authenticated snapshot format.

**Options:**
- **A (recommended):** Remove the NATS KV snapshot cache from the production path now; re-add it later with an authenticated, lineage-bound format and a store-epoch key.
- **B:** Keep it but require a sealing codec, stream/store identity, version validation and CAS; rebuild all existing cache entries.
- **C:** Keep only local/embedded cache for SQLite; no shared KV.

**Recommendation:** A. Snapshots are not needed for the core correctness story, and removing them removes a cross-tenant data-leak surface.

### Q11 — Should this repo converge on the other six modules’ Go/lint/check conventions?

**Context:** The repo uses a Taskfile rather than mise tasks, pins Go 1.26.5 (worktree now 1.27.3), and has no golangci-lint/gofumpt pin or `fmt`/`lint`/`check` gate. The Taskfile approach is good for this repo’s codegen/Docker workflows; the missing gate is the problem.

**Why it blocks:** It determines the toolchain PR and the CI gate. Converging means adding tools to `.mise.toml` and a `check` task; keeping Taskfile-only is fine but still needs the tools and gate.

**Options:**
- **A (recommended):** Keep the Taskfile for codegen/Docker, but add pinned golangci-lint/gofumpt to `.mise.toml` and a `task check` (fmt, lint, vet, test, race, vuln, generate:check). Move nothing else.
- **B:** Fully converge on mise tasks like the other six modules.
- **C:** Minimal: add only `gofmt`/`go vet`, no new tools.

**Recommendation:** A. The Taskfile is better suited to buf/codegen/Docker here; the repo needs the gate, not a task-runner migration.

### Q12 — What release/versioning policy should external adopters rely on?

**Context:** Pre-1.0, tags publish an image, but images report `version=dev`, there is no changelog or test-gated release, and the public API is changing (this review recommends several breaking changes).

**Why it blocks:** It determines how aggressively we break the API and what “supported” means for adopters. The review assumes breaking the Go API is cheap; persisted/wire data is not.

**Options:**
- **A (recommended):** v0.x with a documented “breaking changes allowed between minor versions” policy, a changelog and test-gated releases; tag `v0.3.0` after P0.
- **B:** Stabilize the public API now and commit to semver before any release.
- **C:** Internal-only; no external support promise.

**Recommendation:** A. It matches the early-development context and the user’s stated tolerance for API breakage, while making data-format breaks explicit.
