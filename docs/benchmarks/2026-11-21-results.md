# Events scale results — 2026-11-21

- **Harness:** [`cmd/es-bench`](../../cmd/es-bench) (see [README](./README.md))
- **Backlog:** [2026-11-21_events-scale-benchmark.md](../backlog/2026-11-21_events-scale-benchmark.md)
- **Raw output:** [`results/`](./results) (one JSON per cold/warm run)

## Environment

- Apple M5 Max, 18 CPUs, 128 GB host RAM; Docker Desktop Linux VM with 8 GB
  memory.
- PostgreSQL 17.11, stock settings: `shared_buffers=128MB`,
  `effective_cache_size=4GB`, `synchronous_commit=on`,
  `max_parallel_workers_per_gather=2`.
- Dedicated `es-lite-bench` container on the host SSD; no other workload.
- One workspace (one hash partition), 100 events per synthetic stream, 32-byte
  payloads, 10-event batches with one claim per append.
- **Cold** means the container was restarted after seeding, so shared buffers
  are empty; the host page cache is warm (not dropped). **Warm** is the
  immediately following run over the same data.

## Extrapolation to 100M

The 100M/1% run was **not** executed. Seeding it is a multi-hour write on this
VM: the seed's chunk time grew from ~14 s at 4M events to ~52 s at 50M as the
twelve indexes deepened.

The estimate is nevertheless anchored:

- 100M/1% is 1,000,000 claims, the same count measured at 10M/10%
  (**121 s cold, 129 s warm**). The replay is index-only over the op-bearing
  index, whose size depends on the claim count, not the event count — so the
  scan does not grow from 10M to 100M events.
- Footprint scales with events: 50M = 35 GB, so 100M ≈ **70 GB**.
- Append latency was stable from 10M to 50M (p50 ~2.5 ms), so 100M is
  expected to match.
- A logical restore drill is still an open acceptance item.

## What the numbers say

- **The rebuild is linear in claim-bearing rows, not events.** ~8k claims/s
  across all runs: 100k claims ≈ 13 s, 500k ≈ 56 s, 1.0M ≈ 121–129 s. The
  10M/10% run (10M events, 1M claims) and the 50M/1% run (50M events, 500k
  claims) track their claim counts, not their event counts. `unique_claims`
  inserts dominate; the index-only scan is a small part.
- **The op-bearing index is small.** 15 MB at 100k claims, 76 MB at 500k,
  151 MB at 1M — a fraction of the multi-GB total index footprint.
- **Footprint is ~0.7 KB/event** at a 32-byte payload, about half heap and
  half indexes. Extrapolated to 100M that is ~70 GB.
- **Append p50 is stable at ~2.5 ms** and p99 at ~4–6 ms through the real
  transaction path for a 10-event batch with one claim. The p99 is noisy; the
  max in the 10M/10% run was 21.8 ms.
- **Partitioning does its job.** The same 10M log spread over eight
  workspaces leaves a tenant's partition with 1.25M events and 12.5k claims;
  rebuild and verify take ~1.4 s. The one-partition runs above are the worst
  case.
- **Cold vs warm is modest.** The op index is small enough to stay cached, and
  the claim inserts dominate both runs.

## What is not measured

- **Chain verification.** The bulk seed is unchained; `es-verify all` would
  report the seeded prefix. The append phase writes chained streams, but a
  chain audit over the seeded log is not part of this run.
- **The relay's `published_at` churn.** The seed leaves the column NULL;
  production updates every event once, and the resulting vacuum/bloat at scale
  is unmeasured.
- **A 500M single tenant.** Extrapolated (~350 GB, ~5M claims, ~10–11 min
  rebuild); the pre-500M acceptance list is in
  [the backlog](../backlog/2026-11-21_events-scale-benchmark.md#before-500m-events-in-one-tenant).
- **A logical restore drill.** The harness measures the replay methods, not a
  dump/load cycle. The drill is a separate acceptance item.
- **Production storage and concurrency.** These are local, single-writer
  numbers. Re-run on the deployment's hardware before quoting an SLA.
- **The 8-partition spread.** One partition is the worst case; a uniform
  multi-tenant log is smaller per partition. 100M total over eight partitions
  is the 10M-per-partition case already measured.

## Reproduce

See [README](./README.md). The exact commands for this run were:

```bash
/tmp/es-bench seed -events 10000000 -op-every 100
docker restart es-lite-bench
/tmp/es-bench measure -appends 2000 -batch 10 -claim-every 1 -json
/tmp/es-bench measure -skip-appends -json
```
